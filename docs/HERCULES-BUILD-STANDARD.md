# The Hercules Build Standard

Every Hercules artifact must be recognizably Hercules: distinctive, deliberate, production-minded, and evidence-backed.

## 1. Fly by design
User-facing Hercules work must have a clear visual and product identity. Do not ship generic template presentation when a purposeful Hercules treatment is appropriate. Favor strong hierarchy, clean composition, restrained polish, coherent naming, and details that look intentional rather than generated by default.

## 2. Quality is demonstrated
"Higher quality" is a requirement to prove, not a label to attach. Relevant work must define measurable acceptance criteria and capture evidence such as deterministic tests, validation results, integrity hashes, security checks, performance evidence, or visual review.

## 3. Owned core
Hercules business logic, orchestration, trust controls, and product behavior belong in owned repository code. External infrastructure, runtimes, models, and services remain explicit adapters or dependencies and are never misrepresented as Hercules-owned code.

## 4. Test first where behavior changes
New logic and bug fixes begin with an executable expectation when practical. A feature is not complete merely because code exists.

## 5. Fail closed
Missing authorization, invalid evidence, integrity failure, uncertainty at a protected boundary, or an exceeded authority ceiling must not silently become permission.

## 6. Evidence over claims
Important actions carry verifiable evidence. Never report deployment, verification, ownership, security, recovery, or success that the available evidence does not establish.

## 7. Minimal, composable changes
Prefer the smallest durable primitive that advances the architecture. Do not duplicate verified work. Keep provider-specific concerns behind boundaries and preserve rollback/provenance.

## 8. Exact-head release discipline
Protected changes move through feature branches and pull requests. Security, provenance, owner-code, tests, and other required gates evaluate the exact head before merge. No direct-main shortcuts and no weakening controls to make a build pass.

## 9. Recovery-aware
Consequential features identify rollback, compensation, or manual recovery boundaries before claiming production readiness.

## 10. Finish quality
No placeholder copy, knowingly broken paths, fake metrics, unverified success states, or avoidable rough edges in a release candidate. If a component is intentionally incomplete, label the boundary precisely.

This standard defines how Hercules is built. It does not assert that every artifact is automatically superior; each artifact must earn that conclusion through its own evidence.
